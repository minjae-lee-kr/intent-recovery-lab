# Intent / Recovery

**응답은 사라졌지만, 예약은 남아 있습니다.**

[English](README.md) · [설계 판단](docs/design.ko.md) · [공개·보안 범위](SECURITY.md)

React 클라이언트, 실제 HTTP, SQLite의 영속 기록을 연결한 예약 복구 실험입니다. 브라우저가 응답을 받지 못했는데 서버에서는 예약이 완료되는 상황을 직접 재현합니다.

오래된 요청의 응답이 현재 화면을 덮지 않게 하면서, 예약 키와 요청 내용은 재시도·새로고침 뒤에도 유지합니다.

## 같은 통신 실패, 다른 결과

| 요청 결과를 확신할 수 없을 때       | 실제로 관측하는 결과                                             |
| ----------------------------------- | ---------------------------------------------------------------- |
| 새 키로 같은 내용을 다시 전송       | 예약 두 건. 서버에는 서로 다른 두 요청입니다.                    |
| 원래 키와 요청 내용을 유지해 재시도 | 예약 한 건. 기존 예약 확인 번호를 복구합니다.                    |
| 대기를 중단하고 `404 unseen`을 조회 | 여전히 불확실합니다. 먼저 보낸 요청이 나중에 저장될 수 있습니다. |

앞의 두 행은 커밋 후 응답이 사라진 경우이고, 마지막 행은 원래 요청이 커밋되기 전에 대기를 중단한 경우입니다. 미리 정해 둔 성공 애니메이션이 아니라 실제 실행으로 확인하는 반례입니다. 첫 번째 행은 의도적으로 불완전하게 만든 비교 대상이며, 대화형 클라이언트는 원래 요청을 유지합니다.

**장부가 맞는 것만으로는 충분하지 않습니다.** 별도 [관측 검사기](docs/history-check.ko.md)는 호출자가 대기를 끝낸 쓰기까지 고려해, 사용자가 본 응답을 일관된 실행 순서로 설명할 수 있는지 확인합니다. 이후 조회 한 건을 의도적으로 `404 unseen`으로 바꾸면 최종 장부는 같아도 관측 기록은 모순이 됩니다. 실제 서버 장애가 아니라 검사 능력을 확인하는 대조군입니다. 찾은 순서는 해당 기록을 설명하는 하나의 가능성이며, 실제 커밋 순서나 모든 스케줄의 정확성을 증명하지 않습니다.

## 직접 실행

**Node 24.15–24.x**, **pnpm 11.25.0**이 필요합니다. Windows x64에서 Node 24.15.0 / SQLite 3.51.3과 Node 24.19.0 / SQLite 3.53.3을 검증했습니다. Node 내장 SQLite를 사용하므로 별도 데이터베이스 서비스나 인증 정보가 필요하지 않습니다.

```sh
pnpm install --frozen-lockfile
```

**브라우저에서 복구 흐름 살펴보기:**

```sh
pnpm demo
```

출력된 로컬 주소에서 예약을 준비한 뒤 전송하세요. 기본 장애는 **커밋 후 응답 유실**입니다. 왼쪽 브라우저는 결과를 모르지만 오른쪽 서버 기록에는 예약 한 건이 남습니다. 결과를 복구하고, 언어를 바꾸거나 새로고침하거나, 복구 링크를 다른 탭에서 열어 보세요.

**실행 근거 만들고 확인하기:**

```sh
pnpm experiment  # 복구·프로세스 종료·장부 검증의 일곱 시나리오
pnpm report      # 가장 최근에 생성한 시나리오 보고서 보기

pnpm history     # 시드 세 개, 기록마다 API 연산 13개
pnpm history:report reports/<출력된-history-실행-ID>
```

저장소 루트에서 실행하세요. 각 실험은 새 데이터베이스를 사용하고 자신이 생성한 프로세스를 정리합니다. Git에서 제외한 `reports/` 폴더에 원본 근거와 소스 해시를 저장하며, history 화면은 실제 관측과 의도적으로 바꾼 조회를 구분합니다. 시드는 요청 구성과 발송 순서를 재현하며 OS 스케줄까지 같게 만들지는 않습니다. 보고서는 로컬 출처 기록이며 실행 내용을 암호학적으로 증명하지 않습니다.

테스트·엄격한 타입 검사·프로덕션 클라이언트 빌드는 `pnpm verify`로 별도 실행합니다.

`pnpm retention`으로 실행하는 별도 [보존 기간 실험](docs/retention-boundary.ko.md)은 상대 시스템이 키를 잊은 뒤의 재시도를 다룹니다. 독립된 두 기록을 통해 조회 결과가 없어도 과거 효과를 부정할 수 없는 이유와, 로컬 기한 안에 보낸 요청이 상대 기록 삭제 후 도착하는 경우를 확인합니다. 기존 서버의 보관 정책을 바꾸거나 UI를 추가하지 않습니다.

## 살펴볼 설계 판단

- **화면의 요청 순번과 예약 키는 수명이 다릅니다.** 요청 순번은 클라이언트 컨트롤러와 수명을 함께하고, 예약 키는 새로고침 뒤에도 유지됩니다.
- **불확실함을 하나의 상태로 다룹니다.** 통신 오류, 타임아웃, 대기 중단, 특정 시점의 조회 실패를 예약 거절로 바꾸지 않습니다. 앱 복귀 신호도 결과 조회의 계기일 뿐, 예약 완료의 근거가 될 수 없습니다.
- **관련 기록을 함께 커밋합니다.** 예약 결과, 실제 예약 기록, 정원 변경이 하나의 트랜잭션에 들어갑니다. 같은 키로 요청 내용을 바꾸면 충돌이며, 정원 부족에 따른 거절도 보존합니다.
- **검증 도구의 허점도 확인합니다.** 서버 구현과 별도로 작성한 검사기가 기록 순서대로 정원 판단을 재구성합니다. 다른 요청의 응답, 근거 없는 정원 부족, 이전 실행의 체크포인트가 성공으로 통과하지 않는지 의도적으로 변형해 확인합니다.

## 보장 범위와 한계

**기록을 보존하는 단일 SQLite 트랜잭션 안에서, 하나의 예약 키는 최대 한 건의 예약만 만듭니다.** 실제 프로세스 종료 실험에서는 커밋 전후에 해당하는 결과를 복구했습니다.

서로 다른 키로 표현한 같은 사람의 중복 구매까지 알아내지는 못합니다. 네트워크의 정확히 한 번 전달, 외부 결제의 원자성, 분산 가용성, 인증, 공정성이나 모든 동시 실행 이력의 정합성을 증명하지 않습니다. 실제 자식 프로세스를 종료하지만 정전이나 임의의 디스크 손상을 주입하지는 않습니다. 지연 시간은 장애를 재현하기 위한 설정값이며 성능 성과가 아닙니다.

직접 설계한 가상 데이터 기반 개인 프로젝트입니다. 회사 코드, 내부 설계, 고객 기록, 회사에서의 정량적 성과를 포함하지 않습니다. [AWS의 멱등 API 지침](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), [Stripe의 멱등성 문서](https://docs.stripe.com/api/idempotent_requests), [SQLite의 원자적 커밋 모델](https://sqlite.org/atomiccommit.html)을 참고한 실험이며, 해당 조직과 관계가 있는 프로젝트는 아닙니다.

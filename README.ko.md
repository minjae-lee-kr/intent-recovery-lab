# Intent / Recovery

**응답은 사라졌지만, 예약은 남아 있습니다.**

[English](README.md) · [설계 판단](docs/design.ko.md) · [공개·보안 범위](SECURITY.md)

React 클라이언트, 실제 HTTP, SQLite의 영속 기록을 연결한 예약 복구 실험입니다. 브라우저가 응답을 받지 못했는데 서버에서는 예약이 완료되는 상황을 직접 재현합니다.

핵심 질문은 **“다시 보낼 때 무엇을 유지해야 하고, 지금 무엇까지 알 수 있는가?”**입니다.

## 같은 통신 실패, 다른 결과

| **커밋 이후** 응답이 사라졌을 때    | 실제로 관측하는 결과                                             |
| ----------------------------------- | ---------------------------------------------------------------- |
| 새 키로 같은 내용을 다시 전송       | 예약 두 건. 서버에는 서로 다른 두 요청입니다.                    |
| 원래 키와 요청 내용을 유지해 재시도 | 예약 한 건. 기존 예약 확인 번호를 복구합니다.                    |
| 대기를 중단하고 `404 unseen`을 조회 | 여전히 불확실합니다. 먼저 보낸 요청이 나중에 저장될 수 있습니다. |

미리 정해 둔 성공 애니메이션이 아니라 실제 실행으로 확인하는 반례입니다. 첫 번째 행은 의도적으로 불완전하게 만든 비교 대상이며, 대화형 클라이언트는 원래 요청을 유지합니다.

## 직접 실행

**Node 24.15–24.x**, **pnpm 11.25.0**이 필요합니다. 로컬 검증 환경은 Windows의 Node 24.19.0 / SQLite 3.53.3입니다. Node 내장 SQLite를 사용하므로 별도 데이터베이스 서비스나 인증 정보가 필요하지 않습니다.

```sh
pnpm install --frozen-lockfile
pnpm demo
```

출력된 로컬 주소에서 예약을 준비한 뒤 전송하세요. 기본 장애는 **커밋 후 응답 유실**입니다. 왼쪽 브라우저는 결과를 모르지만 오른쪽 서버 기록에는 예약 한 건이 남습니다. 결과를 복구하고, 언어를 바꾸거나 새로고침하거나, 복구 링크를 다른 탭에서 열어 보세요.

```sh
pnpm experiment  # 실제 HTTP·프로세스 종료 실험과 독립적인 기록 검증
pnpm report      # 가장 최근에 생성한 한·영 보고서를 로컬에서 보기
pnpm verify      # 테스트, 엄격한 타입 검사, 프로덕션 클라이언트 빌드
```

`reports/<실행 ID>/`에 한·영 HTML 보고서와 원본 `evidence.json`을 만듭니다. 각 시나리오는 새 임시 데이터베이스를 사용하고 자신이 생성한 프로세스를 정리합니다. 소스의 실행 전후 해시, 환경, 요청·응답과 검증 결과를 기록합니다. 보고서 명령이 전체 테스트 모음을 실행했다거나 실행 내용을 암호학적으로 증명한다고 주장하지 않습니다.

## 살펴볼 설계 판단

- **화면의 요청 번호와 서버의 예약 키는 수명이 다릅니다.** 화면의 요청 번호는 오래된 응답을 구분합니다. 보존된 예약 키는 재시도·새로고침·여러 탭에 걸쳐 서버의 중복 효과를 막습니다.
- **불확실함을 하나의 상태로 다룹니다.** 통신 오류, 타임아웃, 대기 중단, 특정 시점의 조회 실패를 예약 거절로 바꾸지 않습니다. 앱 복귀 신호도 결과 조회의 계기일 뿐, 예약 완료의 근거가 될 수 없습니다.
- **관련 기록을 함께 커밋합니다.** 예약 결과, 실제 예약 기록, 정원 변경이 하나의 트랜잭션에 들어갑니다. 같은 키로 요청 내용을 바꾸면 충돌이며, 정원 부족에 따른 거절도 보존합니다.
- **검증 도구의 허점도 확인합니다.** 서버 구현과 별도로 작성한 검사기가 기록 순서대로 정원 판단을 재구성합니다. 다른 요청의 응답, 근거 없는 정원 부족, 이전 실행의 체크포인트가 성공으로 통과하지 않는지 의도적으로 변형해 확인합니다.

## 작은 핵심부터 읽기

| 파일                                                 | 확인할 판단                                               |
| ---------------------------------------------------- | --------------------------------------------------------- |
| [`src/client/model.ts`](src/client/model.ts)         | 전송 전 저장, 불확실성, 요청·응답 연결, 늦은 응답 처리    |
| [`src/server/store.ts`](src/server/store.ts)         | 쓰기 직렬화, 함께 커밋하는 기록, 결과의 불변성            |
| [`scripts/experiments.ts`](scripts/experiments.ts)   | 새 키 재시도의 반례, 지연 커밋, 프로세스 종료, 서버 두 개 |
| [`scripts/check-ledger.ts`](scripts/check-ledger.ts) | 예약·정원·판단 이력을 독립적으로 검증                     |

화면과 보고서는 한·영을 지원합니다. 언어를 바꿔도 실험 상태를 유지하며, 키보드 포커스와 동작 줄이기 설정을 반영합니다.

## 보장 범위와 한계

**기록을 보존하는 단일 SQLite 트랜잭션 안에서, 하나의 예약 키는 최대 한 건의 예약만 만듭니다.** 실제 프로세스 종료 실험에서는 커밋 전후에 해당하는 결과를 복구했습니다.

서로 다른 키로 표현한 같은 사람의 중복 구매까지 알아내지는 못합니다. 네트워크의 정확히 한 번 전달, 외부 결제의 원자성, 분산 가용성, 인증, 공정성이나 모든 동시 실행 이력의 정합성을 증명하지 않습니다. 실제 자식 프로세스를 종료하지만 정전이나 임의의 디스크 손상을 주입하지는 않습니다. 지연 시간은 장애를 재현하기 위한 설정값이며 성능 성과가 아닙니다.

직접 설계한 가상 데이터 기반 개인 프로젝트입니다. 회사 코드, 내부 설계, 고객 기록, 회사에서의 정량적 성과를 포함하지 않습니다. [AWS의 멱등 API 지침](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), [Stripe의 멱등성 문서](https://docs.stripe.com/api/idempotent_requests), [SQLite의 원자적 커밋 모델](https://sqlite.org/atomiccommit.html)을 참고한 실험이며, 해당 조직과 관계가 있는 프로젝트는 아닙니다.

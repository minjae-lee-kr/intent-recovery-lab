# 장부가 맞아도, 사용자가 본 결과는 틀릴 수 있습니다

[English](history-check.md) · [기본 실험](../README.ko.md)

이 추가 실험은 클라이언트가 실제로 받은 예약·조회 결과를 하나의 일관된 실행 순서로 설명할 수 있는지 검사합니다. 최종 장부의 합계가 맞더라도, 예약 완료 후의 조회에서 해당 예약이 없다고 응답했다면 중간 관측은 모순일 수 있습니다.

기존 일곱 시나리오는 그대로 유지합니다. 별도 기록기와 검사기가 합성 요청을 실제 HTTP로 보내며, 독립된 Node 프로세스 두 개가 하나의 로컬 SQLite 파일을 공유합니다. 복제 데이터베이스나 외부 결제 시스템을 구현한 실험은 아닙니다.

## 실행과 원본 확인

이 실험이 포함된 `experiment/observed-history` 브랜치 또는 해당 브랜치의 특정 커밋을 체크아웃하세요. 아래 명령은 **저장소 루트 폴더**에서 실행합니다. 이전 `main` 버전인 `46c889e`에는 history 명령이 없습니다.

```sh
pnpm install --frozen-lockfile
pnpm history
pnpm history:check reports/<history-run-id>/seed-104729.json
pnpm history:check reports/<history-run-id>/seed-104729-stale-control.json
```

`history`는 고정된 시드 세 개로 각각 13개 연산을 실행합니다. 출력된 폴더의 `report.txt`를 열면 한·영 결과를 읽을 수 있습니다. `pnpm report`는 여전히 기존 일곱 시나리오의 보고서를 제공합니다. 새로운 `reports/history-*` 폴더에는 전체 `evidence.json`, 개별 원본 기록과 생성 조건을 충족한 조회 반례도 저장합니다. 필수 관측이 빠지면 실행은 실패로 남으며 반례 파일이 생성되지 않을 수도 있습니다. 이 폴더는 Git에서 제외합니다. 기존 보고서와 포트폴리오 허브는 수정하지 않으며 전체 테스트 모음을 실행하지도 않습니다. `history:check`는 서버를 시작하지 않고 저장된 원본 기록을 다시 검사합니다. 종료 코드는 가능한 순서 발견 0, 반례 1, 판정 불가 2, 잘못된 근거 3, 명령 사용 오류 64입니다. stale-control 파일은 반례로 판정되는 것이 예상 결과입니다.

다른 폴더에서는 `pnpm --dir /저장소/절대경로 history:check reports/<history-run-id>/seed-104729.json`을 사용하세요. 스크립트가 지정한 저장소 루트에서 실행됩니다. `node /저장소/절대경로/scripts/check-history.ts /기록파일/절대경로.json`처럼 직접 실행할 수도 있습니다. `node`에 상대 파일 경로를 넘기면 현재 작업 폴더를 기준으로 찾습니다. `run-history.ts`의 보고서 출력 위치는 작업 폴더와 무관하게 해당 스크립트가 속한 저장소 아래입니다.

보고서에는 실행 전후의 소스 파일 해시, Git 상태와 런타임 버전이 포함됩니다. 이는 로컬에서 관측한 출처 정보이며 서명이나 실행 증명은 아닙니다. 두 관측 사이에서 변경했다가 복구한 파일은 탐지하지 못합니다. 시드는 요청 구성과 발송 순서를 재현하며 OS 스케줄이나 예약 확인 번호까지 같게 만들지는 않습니다.

## 이 실험이 구분하는 반례

1. 실제 예약 POST가 완료된 결과를 돌려줍니다.
2. 이후 실제 GET도 같은 결과를 돌려줍니다.
3. 반례 파일에서는 이 GET 응답 한 건만 `404 unseen`으로 바꿉니다.
4. 최종 장부와 나머지 기록은 그대로 유지합니다.

원본 기록에는 가능한 실행 순서가 있어야 합니다. 반례는 최종 장부 검사를 통과하더라도 실행 순서 검사에서 거부되어야 합니다. 이 비교는 최종 상태 확인과 중간 관측 확인이 서로 다른 문제라는 점을 보여줍니다. 변형한 응답은 **검사기의 검출 능력을 확인하기 위한 반례이며, 실제 서버에서 발견한 장애가 아닙니다.**

## 별도로 작성한 순차 모델

[spec.ts](../scripts/history/spec.ts)의 모델은 정원 12명과 빈 예약 기록에서 시작합니다. 실제 저장소나 애플리케이션의 검증 함수를 가져오지 않습니다.

- 처음 보는 요청 키는 정원이 충분하면 예약을 확정하고 수량을 차감합니다. 부족하면 거절 결과를 보존합니다.
- 기존 키와 요청 내용이 같으면 원래 결정과 예약 확인 번호를 돌려줍니다.
- 기존 키에 다른 요청 내용을 보내면 충돌로 처리하며 상태를 바꾸지 않습니다.
- 조회는 보존된 결과 또는 `unseen`을 돌려줍니다.
- 최종 스냅샷은 모든 예약 기록, 확인 번호, 예약 효과와 남은 정원을 모델과 대조합니다.

서로 다른 키도 같은 정원을 사용하므로 키별로 나눠 검사하면 안 됩니다. 확인 번호의 UUID 값을 예측하지 않고, 관측된 값이 일관되며 서로 구별되는지 확인합니다. 실행 순서는 서버가 보고한 `journalSequence`를 따라 정하지 않습니다. 응답의 전체 메타데이터는 보존된 장부와 같아야 하며, 기존 장부 검사기가 기록 순서에 따른 결정, 해시와 수량 보존을 별도로 확인합니다.

검사 대상은 명시한 예약 API 의미이며, 모든 SQL 구문이나 내부 메타데이터 규칙 전체의 정확성을 증명하지 않습니다. 단일 쓰기 경계는 SQLite가 제공하고, 요청의 동일성·결과 보존·API 관측은 애플리케이션이 결정합니다.

## 타임아웃으로 쓰기 연산이 끝나지는 않습니다

부모 프로세스는 각 `fetch` 직전에 호출 이벤트를 기록하고, 전체 응답을 읽거나 대기를 끝낸 뒤 관측 이벤트를 기록합니다. 선후 관계는 하나의 기록기에서 부여한 이벤트 번호로 판단합니다. 반올림한 시간이나 서로 다른 프로세스의 시계를 비교하지 않습니다.

통신 결과가 불분명한 쓰기와 현재 API의 결과 미확정 503은 대기가 끝난 뒤에도 처리 중일 수 있습니다. 검사기는 해당 쓰기가 합법적인 효과를 남기는 경우와, 관측 상태를 설명하는 데 필요하지 않아 제외되는 경우를 살펴봅니다. 통신 오류나 주입한 장애의 이름만 보고 롤백했다고 단정하지 않습니다.

예를 들어 `POST → 타임아웃 → 조회 없음 → 조회 완료`는 두 조회 사이에 예약이 저장되었다면 설명 가능합니다. 반대로 조회가 끝난 뒤에야 호출한 쓰기가 그 이전 조회의 결과를 설명할 수는 없습니다. 아직 결과를 모르는 쓰기에도 호출 시점에 따른 선후 관계를 적용합니다. 각 시도는 별도 식별자를 가지며, 재시도가 앞선 시도를 완료된 것으로 바꾸지 않습니다.

모든 호출자의 대기가 끝나면 부모는 두 서버에 종료를 요청합니다. 각 서버는 실제 `close()`가 이미 받은 요청의 처리를 마칠 때까지 기다린 뒤 실행·프로세스 인스턴스·대상·PID가 연결된 응답을 보냅니다. 부모는 두 응답과 정상 종료를 모두 확인한 뒤 새 읽기 프로세스로 최종 장부를 조회합니다. 이 경계가 있어야 더 늦게 저장될 효과를 놓치지 않습니다. 일정 시간 기다리거나 `fetch` Promise가 끝났다는 사실만으로 대신하지 않습니다. 강제 종료는 정리 수단이며 정상적인 처리 완료 확인으로 취급하지 않습니다.

## 결과를 읽는 방법

| 결과           | 의미                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Witness        | 이 유한한 관측 기록을 설명하는 순서가 하나 이상 있습니다. 반환한 순서는 별도 검사기로 다시 실행합니다.                            |
| Counterexample | 제한된 탐색 공간을 모두 확인했지만 가능한 순서가 없거나, 실제 응답·장부가 약속된 형식을 위반했습니다.                             |
| Inconclusive   | 탐색 한도, 지원하는 기록 크기 또는 종료 후 관측이 충분하지 않습니다. 성공이나 일관성 결함으로 단정하지 않습니다.                  |
| Invalid        | 근거의 식별자, 이벤트 순서나 필수 구조가 잘못되어 분석할 수 없습니다. 실제로 받은 잘못된 서버 응답은 형식 위반 반례로 구분합니다. |

의미 검사기 자체는 간단하지만 정상적인 기록도 허용합니다. **실험 전체**는 여기에 두 서버 참여, 실제로 겹친 요청 구간, 같은 키 재시도, 변경한 요청의 충돌, 정원 부족 거절, 미확정 쓰기 두 건, 이른 조회의 `unseen`, 이후 보존된 두 결과, 반례에 사용할 정상 조회를 모두 요구합니다. 빠진 항목이 있으면 실험을 통과로 처리하지 않습니다. 실행 범위와 의미 판정은 별도 필드로 남습니다.

최대 연산 수는 16개, 미확정 쓰기는 두 개입니다. 기본 탐색 한도는 방문 상태 100,000개와 2초입니다. 한도를 넘으면 판정 불가이며 통과로 바꾸지 않습니다. 검사기는 모델 상태와 처리한 연산 집합을 함께 기억합니다. 공유 정원을 임의로 분리하거나 처음 발견한 불가능한 순서를 전체 실패로 간주하지 않습니다. 제시한 순서는 가능한 설명 하나이며 실제 커밋 순서나 중복 시도 중 어느 것이 저장을 수행했는지 확정하는 근거는 아닙니다.

## 검사기 자체의 검증과 한계

[집중 검증](../tests/history-check.test.ts)은 정상적인 지연 저장, 오래된 조회, 미래의 미확정 쓰기, 겹친 요청의 양쪽 승자, 같은 키의 불확실성, 너무 이른 정원 부족 거절, 확인 번호 변경, 근거 변조와 탐색 한도를 다룹니다. 작은 기록은 별도로 작성한 순차 규칙과 단순한 순열 검사기로도 비교합니다. 이 비교기는 실제 검사기나 모델을 가져오지 않습니다. 순서 재검증기는 완료된 연산 누락, 중복 단계와 선후 관계 위반을 거부합니다. [I/O 검증](../tests/history-io.test.ts)은 실제 두 프로세스와 조회 반례를 실행합니다.

순서 재검증기는 탐색과 별개로 순서·누락을 확인하되 같은 순차 모델을 사용합니다. 별도 모델을 구현한 것은 작은 순열 비교기입니다. 따라서 탐색과 재검증기가 함께 사용하는 규칙 자체의 오류를 재실행만으로 발견할 수 있다고 주장하지 않습니다.

이 작은 검사기 역시 결함이 있을 수 있는 새 코드입니다. 검증된 범용 도구를 대체하거나 구현의 정확성을 증명하지 않습니다. 진행 가능성, 성능, 정전 안전성, 모든 스케줄, 네트워크의 정확히 한 번 전달이나 외부 효과의 원자성은 검사하지 않습니다. HTTP 요청 구간이 겹친다고 SQL이 동시에 실행되었다는 뜻도 아닙니다. 회사 코드나 비공개 운영 데이터는 포함하지 않습니다.

## 참고 자료

순차 명세와 실제 선후 관계는 [Herlihy와 Wing의 논문](https://cs.brown.edu/~mph/HerlihyW90/p463-herlihy.pdf)을 따릅니다. 미완료 연산도 호출 시점의 제약을 지켜야 한다는 세부 사항은 [Sela·Herlihy·Petrank의 보완 설명](https://arxiv.org/html/2105.06737v2)에 명시되어 있습니다.

[Porcupine](https://github.com/anishathalye/porcupine)은 널리 사용되는 모델 기반 검사 도구이며 이 실험의 구현은 아닙니다. [Jepsen의 실험 설계 설명](https://jepsen.io/analyses/tendermint-0-10-2)은 미확정 쓰기가 많아질수록 가능한 해석이 늘어나 결함을 발견하기 어려워지는 이유를 다룹니다. 저장소의 경계는 [SQLite 격리 문서](https://www.sqlite.org/isolation.html)를 참고했습니다.

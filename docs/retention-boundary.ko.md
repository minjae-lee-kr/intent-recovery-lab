# 키는 남았지만, 중복 방지 기록은 사라졌습니다

[English](retention-boundary.md) · [기본 실험](../README.ko.md)

이 실험의 서버는 같은 키여도 보관하던 응답을 지운 뒤에는 새 요청으로 처리합니다. 각자의 SQLite 기록을 가진 두 서비스를 실제 HTTP로 연결합니다. 상대 서버는 작업 결과(effect)를 저장한 뒤 응답을 보내지 못하고, 나중에는 키에 연결된 응답 기록도 삭제할 수 있습니다. 그 뒤 `absent`를 조회해도 처음 요청이 실행되지 않았는지, 실행 후 응답 기록만 사라졌는지 구별할 수 없습니다.

기존 예약 서버는 요청 이력을 계속 보존합니다. 이 실험은 별도 실행 예제이며 앱의 보관 정책을 바꾸거나 실제 제공사를 연동하지 않습니다.

## 다섯 조건 실행하기

기본 프로젝트의 Node/pnpm 환경에서 저장소 루트를 기준으로 실행합니다.

```sh
pnpm install --frozen-lockfile
pnpm retention
```

출력된 `reports/retention-*/report.txt`에서 한·영 결과를 읽고, `evidence.json`에서 HTTP 관측, 두 시스템의 기록, 시도 식별자, 감사 결과와 소스 출처를 확인합니다. 추가 UI는 없습니다. 실행기가 만든 루프백 프로세스를 종료하고 기록을 감사한 뒤 임시 데이터베이스를 제거합니다. 보고서에는 JSON과 텍스트만 남으며 DB 파일이나 로컬 파일 경로는 내보내지 않습니다. 관련 통합 검사는 `node --test tests/retention.test.mjs`로 실행합니다. `pnpm retention`이 전체 테스트 모음까지 실행하는 것은 아닙니다.

로컬 확정 결과(grant)는 상대 확인 번호를 근거로 `grants` 테이블에 저장한 결과입니다. 미확정 요청과 조회 이력은 별도로 보존하므로, 확정 결과가 0건이어도 로컬 기록이 없다는 뜻은 아닙니다.

| 조건                                         | 상대 효과 / 로컬 확정 결과 | 확인할 차이                                                                                                    |
| -------------------------------------------- | -------------------------: | -------------------------------------------------------------------------------------------------------------- |
| 응답 두 번 유실 후 보존된 결과 조회          |                      1 / 1 | 기간 안의 POST는 같은 확인 번호를 재사용하고, 삭제되지 않은 기록은 최소 보존 기간 이후에도 복구할 수 있습니다. |
| 삭제 이후 같은 키로 재시도                   |                      2 / 1 | 로컬에서 한 번만 확정해도 상대 효과는 반복될 수 있습니다.                                                      |
| 기한 이후 전송 거절; 첫 요청은 실행됨        |                      1 / 0 | 미확정 상태로 남고 새로운 POST를 보내지 않습니다.                                                              |
| 기한 이후 전송 거절; 첫 요청은 실행되지 않음 |                      0 / 0 | 로컬 HTTP 응답과 전체 DB 테이블이 같아도 상대 이력은 다를 수 있습니다.                                         |
| 로컬 기한 내 전송, 상대 시스템에는 늦게 도착 |                      2 / 1 | 로컬 기한은 이미 전송된 요청을 회수하지 못합니다.                                                              |

매 실행의 실제 결과를 이 기대값과 대조합니다. **“설정한 실험 결과 확인”에는 효과가 두 번 발생한 반례도 포함됩니다.** 해당 조건은 보고서에서 `remoteEffectAtMostOnce: false`로 따로 표시합니다.

## 전송 거절 정책은 상대 시스템의 수신 기한이 아닙니다

로컬 시스템은 전송 전에 키, 요청 내용, 최초 전송 시각과 계약을 저장합니다. 재전송 기한은 최초 전송 + 보존 기간 1,000 − 가정한 여유 예산 100입니다. 기한 이후 조회 결과가 없으면 `needs-reconciliation`으로 남습니다. 키를 새로 만들거나 재시도 권한으로 해석하지 않습니다. 일치하는 확인 번호를 받으면 이후에도 복구할 수 있습니다. 모호한 조회 결과로 새 전송을 허용하지 않는 대신, 한 번도 실행되지 않은 요청도 미확정으로 남깁니다.

재시작하면 시계의 신뢰를 미확인으로 보고, 미확정 POST를 거절합니다. 저장한 시각보다 과거로 시계를 되돌리는 것도 거절합니다.

다섯 번째 조건은 이 정책에 남아 있는 시간 가정을 드러냅니다.

```mermaid
sequenceDiagram
    participant L as 로컬 시스템
    participant R as HTTP 중계
    participant D as 상대 시스템
    L->>D: 논리 시각 10000에 첫 POST
    D->>D: 효과 저장; 키는 최소 11000까지 보존
    D--xL: 응답 유실
    L->>R: 기한 10900 이전인 10020에 같은 키 재전송
    Note over R: 실제 요청을 보류
    Note over L,D: 부모가 두 실험 시계를 12000으로 진행
    D->>D: 만료된 중복 방지 기록 삭제; 효과 이력은 유지
    R->>D: 동일한 재시도 요청 전달
    D->>D: 보존된 키가 없어 두 번째 효과 저장
    D-->>L: 새 확인 번호; 로컬 결과는 한 번만 확정
```

중계는 본문, 키, 시도 식별자를 유지합니다. 부모가 요청을 보류하고 풀어 주며 순서를 정합니다. 논리 시각의 차이는 실제 네트워크 지연 측정값이 아닙니다. 설정한 여유 예산이 현실의 통신 한도를 보장하지도 않습니다. 전달 시간이 제한되지 않으면 기한 안에 보낸 요청도 삭제 이후 도착할 수 있습니다. 상태 조회는 다음 POST를 원자적으로 허가하는 연산이 아닙니다.

## 직접 구현한 부분과 독립적으로 확인한 부분

[`worker.mjs`](../scripts/retention/worker.mjs)에 두 실험 역할이 있습니다. 상대 트랜잭션은 가상 효과와 중복 방지 응답을 함께 저장하고, 만료 후에는 응답 기록만 삭제합니다. 로컬 트랜잭션은 받은 확인 번호와 로컬 확정 결과를 함께 저장합니다. 두 시스템을 아우르는 트랜잭션은 없습니다. 실행기는 부모 IPC 연결이 있어야 시작하며 시계·삭제·응답 유실은 부모 제어입니다. HTTP 관리 API로 제공하지 않습니다.

[`check.mjs`](../scripts/retention/check.mjs)는 실행기의 검증 함수를 가져오지 않습니다. 기록 순서대로 보존 상태를 재구성하며, 최소 보존 기간 전에 기록을 삭제한 실행은 만료 반례로 인정하지 않습니다. 각 로컬 확정 결과는 해당 시도에서 받은 정확한 확인 번호와 일치해야 합니다. 같은 키로 받은 과거 확인 번호가 있다는 것만으로는 부족합니다. [`sensitivity.mjs`](../scripts/retention/sensitivity.mjs)는 변경하지 않은 복사본과 잘못된 확인 번호·조기 삭제 등을 넣은 다섯 변형을 비교합니다. 두 미확정 사례의 전체 로컬 테이블과 응답 본문은 식별자를 바꾸지 않고 그대로 대조합니다.

감사기는 종료 후 상대 시스템의 이력도 읽지만, 재시도 정책에는 그 권한이 없습니다. 정책도 그 이력을 조회할 수 있다고 가정하면, 구현하지 않은 복구 API에 의존하게 됩니다. `needs-reconciliation`은 미해결 상태이며 운영자 판단, 환불, 보상 처리나 미실행 증명을 구현한 것은 아닙니다.

## 한계와 참고 문서

이 계약의 보존 기간은 상대 시스템이 수락·커밋한 때부터의 **최소 기간**입니다. 기한이 지나면 삭제할 수 있지만, 남아 있는 확인 번호까지 무효가 되지는 않습니다. 부모가 주입한 두 시계는 속도와 기준점이 같습니다. 현실의 시계 신뢰, 통신 시간 한도, 여러 조정자 간 배제나 일반적인 안전한 재시도를 보장하지 않습니다. 하나의 로컬 실행기가 같은 의도의 시도를 직렬화합니다. 진행 가능성, 결제 원자성, 정전 내구성, 특정 제공사의 동작이나 전역 exactly-once를 주장하지 않습니다.

기존 `sourceEvidence()`로 실행 전후의 소스 목록, Git 상태와 Node/SQLite 버전을 기록합니다. 해시는 출처 관측이며 실행 인증이 아닙니다. 중간에 수정했다가 되돌리거나 악의적인 실행 환경이 기록을 바꾸는 경우까지 탐지하지 않습니다. 감사기는 관측 기록의 완전성과 진위를 신뢰하며 범용 분산 이력 검사기가 아닙니다. 조회 결과가 없다는 사실로 과거 실행까지 부정할 수 없습니다.

- [Stripe API v1 멱등성](https://docs.stripe.com/api/idempotent_requests)은 키 삭제 이후 재사용이 새로운 요청이 됨을 설명하고 최소 24시간 보존을 명시합니다. 이 예제의 논리 단위 1,000은 그 기간과 무관하며 Stripe의 응답 의미나 API v2를 구현하지 않습니다.
- [PayPal 멱등성](https://developer.paypal.com/api/rest/reference/idempotency/)은 재시도 안내를 각 API가 ID를 보존하는 기간과 연결합니다. 모든 시스템에 적용되는 보존 계약은 아닙니다.
- [Node SQLite](https://nodejs.org/api/sqlite.html)의 동기 데이터베이스 API를 사용합니다. 트랜잭션 안에서 네트워크 응답을 기다리지 않습니다.

모든 데이터와 실패 순서는 독립적으로 만든 가상 예제입니다. 기존 [로컬 보안 범위](../SECURITY.md)가 적용되며, 외부 예약 API나 인증 시스템이 아닙니다.

## 실험 결과를 확인하지 못한 경우

`NOT ESTABLISHED`와 종료 코드 `1`은 전체 비교가 성립하지 않았다는 뜻입니다. 이후 실행이 통과하더라도 실패한 실행의 `evidence.json`과 `report.txt`는 보존하세요. `executionError`에서 실험 실행 오류를, `sourceStable`에서 실행 전후에 관측한 소스 변경 여부를 확인합니다. 실행 오류가 없어도 소스가 바뀌면 결과를 인정하지 않습니다.

실험 실행 오류가 발생하면 `executionError.context`에 최초 실패 시점의 관측을 남깁니다. 정리 작업 도중 처음 실패한 경우도 포함합니다.

| 필드                        | 읽는 방법                                                                                                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scenario`, `phase`, `code` | 어떤 조건과 단계에서 어떤 오류 범주가 관측됐는지 나타냅니다. 실패 위치를 좁혀 줄 뿐 원인을 확정하지는 않습니다.                                                     |
| `request`                   | 해당 조건 안에서의 요청 순번, `execute` 또는 `reconcile`, 관측한 HTTP 상태입니다. 상태가 `null`이면 기록하지 못했다는 뜻이며, 요청의 효과가 없었다는 뜻은 아닙니다. |
| `workers`                   | 실행기가 관리하는 프로세스마다 준비 확인과 `close` 이벤트를 각각 관측했는지 나타냅니다. 둘 다 미관측일 수 있으며, 종료 미관측만으로 생존을 판단할 수는 없습니다.    |

이후 정리 작업은 이 기록을 덮어쓰지 않습니다. 실패 문맥에는 원문 예외 메시지, 스택, 경로, 응답 본문과 자식 프로세스의 표준 오류를 넣지 않습니다. 수집 도중 실패하면 일부 사례의 감사 결과를 완성된 비교처럼 내보내지 않으며, 사례 목록은 비어 있습니다.

Windows의 Node 24.15.0에서 소스 [`f0e9ff9`](https://github.com/minjae-lee-kr/intent-recovery-lab/tree/f0e9ff9bc277184e81fcda8f49da338041960e8a)를 검증하던 중 한 실행에서, 첫 사례의 로컬 프로세스를 재시작하기 전에 호출자와 로컬 실행기 사이에 예상하지 않은 `ECONNRESET`이 발생했습니다. 의도한 응답 유실은 이와 별개인 상대 시스템과의 통신에서 일어납니다. 이후 실행은 완료됐지만 최초 오류의 원인은 아직 확인하지 못했습니다. 새 진단 필드는 다음 실패의 기록을 보완하며, 원인 불명의 오류를 수정했다는 뜻은 아닙니다. 통과할 때까지 반복 실행해도 그 원인이 밝혀지는 것은 아닙니다.
